# Codegen generates the Java interface + dynamicType() factory for hand-written interface files

Date: 2026-07-10

## Problem

The runtime has ~10+ hand-written Java interface files that duplicate what codegen already knows about them:

Example — `binding`:
- `codegen/.../BuiltinTreeGen.java:587-606` defines an `InterfaceSpec("binding", ..., methods=[bindingUse_(xx, loc, code)])`.
- `runtime/.../eval/Binding.java:14-19` hand-writes `public interface Binding` with the exact same `bindingUse_(ExprContext, QExprId, Code)` abstract method.
- `runtime/.../eval/Binding.java:21-49` hand-writes a `BindingDynamicType` holder that reconstructs a `TypeObjectDynamic` from the same metadata (name, jvmClass, typeId, dropKind, aspect identity) that the spec already carries.

The `javaTraitName=null` on the spec is the smoking gun: it means "don't generate the Java interface" — because the hand-written one exists.

## Goal

Codegen becomes the single source of truth:
- Codegen emits `compilerxyz.gen.Binding.java` (and equivalent for every affected interface).
- The emitted file contains both the Java `interface` with abstract methods AND the `dynamicType()` factory returning a `TypeObjectDynamic` built from the spec.
- **No default method bodies.** Interfaces without implementations are meaningless; every implementer must provide the body. If codegen ever finds itself wanting to emit a `throw new AssertionError("user did not provide...")` default, that means the spec is incomplete or the interface shouldn't have been declared.
- Hand-written interface files are deleted; all callers switch imports from `compilerxyz.eval.X` (or wherever) to `compilerxyz.gen.X`.

## Design

### Extend `InterfaceSpec`

Add fields (nullable so existing non-migrated specs stay working):
- `typeIdConstantName: String?` — e.g. `"TYPE_ANY_BINDING_DYNAMIC_TYPE_ID"`. Codegen emits `GenTypeIds.<name>` in the factory. Required when `javaTraitName != null` for codegen to emit the factory.
- `dropKind: ObjectDropKind?` — defaults to `DYNAMIC_LIGHT`. Emitted into the factory.
- (Existing `builtinUniqueId` already drives `identityMethodName` for the aspect identity — no new field needed for that.)
- (Existing `javaTraitName` becomes required for codegen migration — every migrated interface has one.)

### Extend `InterfacesGen.writeTrait`

Currently the method emits:
1. Abstract Java methods for each `Rust`-case method (already correct).
2. `dynamicType()` returning `new $T()` referencing `javaDynamicTypeClass` (used only in tests; will go away after `MethodArgs.Rust` normalization).

Replace with:
1. Abstract Java methods for each method (unified after `MethodArgs` refactor — see below).
2. `dynamicType()` static returning `TypeObjectDynamic` via inline nested `Holder` class:
   ```java
   static Type dynamicType() { return DynamicType.INSTANCE; }
   final class DynamicType {
     static final TypeObjectDynamic INSTANCE = build();
     private DynamicType() {}
     private static TypeObjectDynamic build() {
       var identityAspects = new TList<Unique>();
       identityAspects.add(<GenBuiltinInterfaces.builtin<Name>IfaceIdentity>());
       return new TypeObjectDynamic(
         <GenTypeIds.typeIdConstantName>,
         <spec.name>,
         JavaInternalName.of("compilerxyz/gen/<spec.javaTraitName>"),
         JavaDataDescriptor.fromClass(<spec.javaTraitName>.class),
         new TList<>(), new TList<>(),
         <spec.dropKind>,
         identityAspects,
         new TList<>(), new TList<>(),
         Opt.none(), Opt.none(), Opt.none());
     }
   }
   ```
3. Delete the `spec.javaDynamicTypeClass()` code path — no longer needed since factory is inline.

### Prerequisite: `MethodArgs` normalization

Do the `MethodArgs.Rust` → unified-record refactor **first** (still-pending step 2 of the earlier plan). Reason: with only one variant, `writeTrait` emits a Java abstract method for every method uniformly, so the migrated Java interfaces have their methods emitted. If we skip this, we'd need extra logic in `writeTrait` about "which methods get emitted" and end up with the same Source/Rust asymmetry we're trying to eliminate.

Recipe for `MethodArgs` normalization (from earlier discussion):
1. Delete `MethodArgs.Rust`. Rewrite 15 BuiltinTreeGen callers + 2 test callers as `MethodArgs.Source(TList<NamedTypeRef>)` — merge each Rust's `context+data` into a single flat field list.
2. Delete `MethodArgs` sealed interface entirely (only one variant). Change `Method`'s `args` field to `TList<NamedTypeRef>` (or wrap as `ArgRecord`).
3. Delete `MethodSig` (now unused).
4. In `InterfacesGen`, delete the Rust cases in `dataFieldNames` and the main switch. `writeTrait` now always emits abstract methods from the record fields.
5. In `writeTrait`, delete the "skip Source" branch — every method emits a Java abstract method with one parameter per record field.

### Migration order per interface

For each hand-written interface (starting with `binding`):

1. **Ensure the InterfaceSpec is complete.** Set `javaTraitName`, `typeIdConstantName`, `dropKind`. Convert methods to unified record shape.
2. **Verify codegen output.** Build codegen, generate, inspect `runtime/target/generated-sources/codegen/compilerxyz/gen/<Name>.java` — must have (a) the abstract methods and (b) `dynamicType()` returning a `TypeObjectDynamic` matching what the hand-written file used to build.
3. **Delete the hand-written file.** e.g. `rm runtime/.../eval/Binding.java`.
4. **Sweep imports.** Every file using `compilerxyz.eval.Binding` switches to `compilerxyz.gen.Binding`. Include:
   - Java `import` statements.
   - `implements Binding` declarations.
   - JVM-internal-name strings like `"compilerxyz/eval/Binding"` — hit `SourceObjectEmitter.java:49,192` for `Binding`.
5. **Verify build + tests.** Baseline must hold at 47/59 (7F+5E).
6. **Commit.**
7. Move on to next interface.

## Target migration — complications for the fresh session

`target` interface (`runtime/.../eval/dynamic/Target.java`) is substantially more work than `binding` because it mixes three concerns:

- **9 abstract methods** to add to the spec: `bind`, `castException`, `seq`, `tryFinally`, `drop`, `stage`, `if_`, `tryCatchFinally`, `match_`. Currently the `target` spec in `BuiltinTreeGen.java:667` has `TList.<Method>of()` (empty). Each needs its arg-record and ret plumbed.
- **4 utility methods with real bodies** (`targetMaybeBindSub`, `targetCodeToBindSub`, `targetBindSubRecord`, `targetBindSubTuple` — ~50 lines total) — these aren't "meant to be implemented", they're helpers. Per the no-default-body rule, they must be moved OFF the interface entirely, either as static helpers on a companion class or as free functions somewhere sensible. Do not duplicate them into every implementer.
- **5 nested records** (`BindResult`, `RecordBindField`, `TupleBindSlot`, `IfBranch`, `TryCatchClause`) + **2 private static helpers** (`sortBindSubs`, `emitCompositeInstantiation`) currently in the interface file. Records can stay as static-nested on the generated interface (spec extension needed) or move to a companion. Static helpers move with the utility methods they support.
- **Only 1 implementer** (`TargetDynamic`) — but it doesn't override `targetCastException`, so migration must either supply a real implementation there or explicitly panic.

Suggested Target migration order:
1. Extract utility methods + private helpers into a new hand-written `TargetHelpers` class (companion, not part of the migration to codegen). Move the 5 records into `TargetHelpers` too (or leave as static-nested — the spec-extension for nested records is a separate design question).
2. Add explicit `targetCastException` implementation to `TargetDynamic` (or explicitly reject).
3. Update the `target` InterfaceSpec: 9 abstract methods with named-field arg lists, plus `javaTraitName="Target"`, `typeIdConstantName="TYPE_ANY_TARGET_DYNAMIC_TYPE_ID"`.
4. Delete `runtime/eval/dynamic/Target.java`.
5. Sweep imports (grep `compilerxyz.eval.dynamic.Target`).
6. Update JVM-internal-name strings referencing `compilerxyz/eval/dynamic/Target` → `compilerxyz/gen/Target` (if any).
7. Verify baseline.
